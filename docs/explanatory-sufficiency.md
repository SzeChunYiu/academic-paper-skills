# 解释充分性：论文到底讲清楚了吗？

[English](explanatory-sufficiency_EN.md)

一篇论文可以很简洁、语法也完全正确，但读者仍然看不懂，因为作者把真正需要的推理步骤压缩掉了。本指南处理的是 **explanatory underspecification（解释不足 / 过度压缩）**，目标不是把论文写长，而是让目标读者能够真正重建作者的科学思路。

## 核心问题

AI 辅助写作很容易从一个名词直接跳到结论：

```text
We introduce X, which improves Y.
```

句子可能没有事实错误，但读者仍然不知道：

- X 到底改变了什么；
- 为什么这种改变会影响 Y；
- Y 怎么测量；
- 相对什么 baseline 才叫提升；
- 这个结论在哪些条件下不成立。

因此正确的问题不是“还能不能再短一点”，而是：

> 目标读者能不能在不替作者补前提的情况下，自己重建这条科学逻辑？

## 最小充分解释

每个重要的新概念只补读者真正需要的解释元素：

1. **Identity** — 它是什么？
2. **Purpose** — 为什么这里需要它？
3. **Mechanism / logic** — 它如何工作，或者这个推断为什么成立？
4. **Evidence / observable consequence** — 我们怎么知道？
5. **Boundary / assumption** — 在什么条件下成立？
6. **Connection** — 它让下一步什么事情变得可理解或可检验？

不是所有概念都要六项全部解释。领域内非常标准的术语可能不需要展开；论文核心的新机制则可能需要大部分元素。

## 自适应展开

解释篇幅优先放在三个因素都高的地方：

`中心性 × 陌生度 × 推理依赖程度`

更应该展开：

- 论文核心新概念；
- headline claim 所依赖的机制；
- 对目标读者陌生的跨学科方法；
- 会改变解释的关键分析选择；
- 尺度不直观的新 metric；
- 反常或令人意外的结果；
- 会改变结论边界的失败场景；
- 主结论依赖的重要假设。

可以压缩：

- 目标领域真正标准的知识；
- 前文已经解释清楚的定义；
- 没有科学后果的实现细节；
- 不改变解释的二级 robustness 检查。

## 隐藏前提检查

对每个重要的 A → B 推断问：

> B 要从 A 推出来，读者必须额外知道或相信什么？

缺失前提可能是：

- 可以安全假设的共同知识；
- 本文前面已经建立；
- 专业但关键，需要补一句；
- 本文特有的假设，必须明确写出；
- 有争议的推断，需要证据或收敛语气；
- 完全没有支撑的跳跃，应删除或补证据。

`therefore`、`thus`、`suggesting that` 这些词本身并不能提供缺失逻辑。

## 各章节应该解释到什么程度

### Introduction

要让读者理解：问题是什么、为什么现有知识没有解决、本文究竟问什么、贡献属于哪一类，以及为什么这个贡献有可能解决前面的问题。不要为了“解释充分”写成教科书式历史回顾。

### Methods

对会影响解释的关键选择，应说明：

`做了什么 → 怎么做 → 为什么这样选 → 哪些假设/参数会影响解释`

只列软件、包名、模型名或方法名，不等于科学方法解释。

### Results

一个主要 Results block 通常应让读者恢复出：

`局部问题 → 必要 setup/comparison → observation/estimate → evidence/uncertainty → 有边界的推断 → 为什么下一分析有必要`

不需要重复完整 Methods，但如果没有一两句方法提醒就无法理解结果，就应该保留那部分。

### Discussion

不要从一个 finding 直接跳到宏大意义。中间的科学解释必须可见：

`finding → interpretation → 与替代解释/已有证据的关系 → boundary → implication`

### Figures

正文负责告诉读者 **应该看什么、为什么重要**。图注负责告诉读者 **图里是什么、应该怎么读**。不要让正文变成图注复读，也不要让图注独自承担整个科学解释。

### Equations

核心公式需要定义变量，并解释公式在科学上承担什么作用。对形式领域专家不必重复标准记号；跨学科论文则可能需要一两句直觉解释。

## 常见解释不足模式

- 只报方法名，没有科学理由；
- 只给一个 metric 数字，没有 baseline、尺度或 uncertainty；
- 声称机制，但没有说明哪条证据排除了替代机制；
- 只写“见 Fig. 3”，没有告诉读者应该看到什么模式；
- 写出公式但没有解释各项的概念含义；
- 用引用代替当前上下文真正需要的局部解释；
- 用一句 novelty sentence 同时塞入问题、方法、机制、benchmark 和意义；
- 大量名词堆叠，把本应通过从句说明的关系压扁了。

## 不要走向过度解释

以下情况应该删减或转移：

- 定义重复但没有新功能；
- 给专业读者讲领域常识的教科书内容；
- 每个 Results 分析前都重新讲一遍背景；
- Methods 变成教学教程而不是可复现说明；
- 解释代码/仓库操作而不是科学方法；
- 图中模式已经一目了然，却逐 panel 逐句复述。

目标是 **第一次解释就充分**，后续只在读者需要时做简短提醒。

## Reader reconstruction checklist

对每个核心概念、结果、机制和关键方法选择，检查目标读者能否复述：

- 它是什么？
- 为什么在这里出现？
- 它怎么工作，或者这个推断为什么成立？
- 什么证据或 comparison 支撑它？
- 哪个重要假设或边界适用？
- 它改变了什么，或者让下一步什么成为可能？

如果好几个问题都只能靠猜，那么即使文字很“顺”，仍然是解释不足。

## 研究依据

当前 Nature Portfolio 的写作指导明确提醒作者，不要假设所有读者都拥有理解研究所需的专业背景。旗舰 Nature 要求文章能够被其他学科读者理解，并指出高度技术性的论文有时反而需要更长一点的 summary paragraph，让非专业读者理解背景以及新结果改变了什么。Nature Climate Change 对 Methods 的要求直接概括为 **what was done, how it was done, and why**，同时也鼓励在正文中保留有助于读者理解结果的简短方法说明。

读者理解研究也支持这个方向。Gopen 与 Swan 的 reader-expectation 方法强调上下文、句间连接、动作和新信息位置。科学说明文实验研究表明，同时改善文本内部思想之间的关系以及文本与读者已有知识之间的连接，有助于更深层理解。关于 jargon 的实验研究还显示，即使给出术语定义，过强的专业术语密度仍可能降低 processing fluency。

因此最实用的原则是：

> 对读者已经知道的内容保持简洁；对读者无法安全自行推断的科学逻辑明确展开。
